# RuoYi Harness — Security Model

## 1. Threat model

Harness executes dynamically authored script content. Treat every script as **untrusted code**, including scripts generated by trusted AI systems or administrators.

Primary threats:

- escaping the script sandbox into the JVM
- arbitrary filesystem/process/network access
- bypassing RuoYi authorization
- invoking capabilities not intended for the current user
- denial of service via infinite loops, excessive memory/output, or capability call storms
- data exfiltration through logs or responses
- cross-user state leakage
- publishing malicious or invalid versions
- forged app/version/action identifiers
- sensitive data leakage in audit logs

The security model assumes the host Java/Spring code and administrator authentication are trusted, but mistakes in script source are expected.

---

## 2. Security boundary

The primary boundary is:

```text
UNTRUSTED
script source + script input
        |
        v
restricted Script Runtime
        |
        v
Capability Bridge
        |
-------- SECURITY BOUNDARY --------
        |
        v
TRUSTED
RuoYi authentication / authorization / Spring services / database
```

No alternative path may let scripts reach trusted host resources.

---

## 3. Mandatory sandbox properties

A script must not be able to directly access:

- JVM host classes
- Java reflection
- Spring ApplicationContext
- class loaders
- MyBatis/JPA/JDBC/DataSource
- filesystem APIs
- process execution
- native libraries
- environment variables
- JVM system properties unless explicitly copied as safe values
- thread creation
- unrestricted timers/background jobs
- unrestricted outbound HTTP/network sockets
- raw authentication tokens

For GraalVM/Polyglot, configure deny-by-default access and add regression tests that attempt known escape paths.

A configuration setting alone is not considered proof of sandboxing. Security tests are required.

---

## 4. Capability authorization

Every capability invocation performs authorization at execution time.

Never rely on UI visibility or script validation as an authorization mechanism.

Required flow:

```text
capability name
 -> registry lookup
 -> validate input schema
 -> read trusted current user context
 -> verify required RuoYi permission(s)
 -> apply risk/policy rules
 -> execute handler
 -> validate/sanitize output
 -> audit result
```

If a script knows the name of a capability but the current user lacks permission, the call must fail.

---

## 5. Identity propagation

User identity must come from the normal RuoYi security context on every HTTP request.

Scripts may read a sanitized identity projection, but cannot supply identity fields used for authorization.

Forbidden pattern:

```json
{
  "userId": 1,
  "action": "delete"
}
```

where `userId` from script/client input controls authorization.

Correct pattern:

```text
Spring Security / RuoYi context -> trusted CapabilityContext.userId
```

---

## 6. Version integrity

Published versions are immutable.

Store a cryptographic source hash, preferably SHA-256, with each validated/published version.

Before executing a cached compiled artifact, its identity must correspond to the immutable version/source hash.

Publishing is a permission-controlled administration operation.

Recommended permissions:

```text
harness:app:list
harness:app:create
harness:app:edit
harness:app:validate
harness:app:publish
harness:app:rollback
harness:app:disable
harness:audit:view
```

---

## 7. Denial-of-service controls

At minimum enforce:

- script execution deadline
- maximum script source size
- maximum input size
- maximum output size
- maximum capability calls per execution
- maximum UI node count
- maximum log events per execution
- pagination/row limits inside capabilities

Where the selected engine supports hard resource constraints, use them. Where it does not, isolate execution as strongly as practical and make timeout behavior testable.

Do not permit script-created long-lived background threads.

---

## 8. Network model

Dynamic scripts have **no direct network access** by default.

If outbound integration is required, expose a purpose-built capability such as:

```text
integration.erp.queryOrder
integration.webhook.sendApproved
```

That capability can apply:

- destination allowlist
- authentication management
- rate limits
- request schema validation
- audit/redaction

Do not expose a generic unrestricted `fetch(url)` capability in SDK v1.

---

## 9. Database model

Dynamic scripts have **no raw SQL capability**.

Do not expose generic APIs like:

```text
sql.execute
jdbc.query
mybatis.mapper
```

Business data access must be represented through explicit capabilities backed by normal services.

This preserves:

- domain validation
- row-level constraints where implemented
- tenant filtering
- transaction behavior
- permission checks
- auditability

---

## 10. UI security

The browser renderer must not render arbitrary raw HTML by default.

Text values are treated as text, not HTML.

If a future `richText` component is introduced, sanitize its content using a strict allowlist.

Do not allow scripts to inject:

- `<script>` tags
- event-handler attributes
- arbitrary `javascript:` URLs
- arbitrary Vue component names
- executable browser code

The renderer maps approved `type` values to statically imported components.

---

## 11. Cross-site request protections

Runtime/action APIs inherit RuoYi's authentication and request security model.

Preserve relevant CSRF/CORS/token protections based on the chosen RuoYi edition and authentication model.

Do not add permissive CORS solely for dynamic apps; they are part of the same host application.

---

## 12. Audit logging

Every script execution records:

- user ID
- app ID/key
- immutable app version ID
- page/action entry
- trace ID
- duration
- result status
- capability call count
- sanitized error code

Every capability call records:

- trace ID
- capability name/version
- user ID
- risk level
- duration
- result status

Sensitive request/response bodies should not be logged by default.

Provide a redaction mechanism for fields such as:

```text
password
token
secret
authorization
idCard
bankAccount
phone
email
```

Actual redaction rules should be configurable and domain-aware.

---

## 13. Administration safety

Publishing should require explicit admin intent and must not happen automatically merely because an AI generated code successfully.

An AI integration may create/edit/validate drafts. Publication must pass the same authenticated permission path as human publication.

The project may later support policy-controlled auto-publish, but that must be an explicit administrator setting, never the default security assumption.

---

## 14. Required security tests

The final test suite must include attempts to:

1. access `java.lang.System`
2. access `Runtime.exec`
3. access Java host classes through polyglot escape paths
4. read a local file
5. read environment variables
6. open a network connection directly
7. create a thread/background task
8. exceed execution timeout
9. exceed capability-call quota
10. return an oversized UI payload
11. invoke an unknown capability
12. invoke a known capability without permission
13. forge another user's identity in input
14. edit a published version
15. execute an app that has been disabled
16. inject raw HTML/script into a normal text component
17. call an action against an unauthorized app

A release should fail if any sandbox escape regression test succeeds.
